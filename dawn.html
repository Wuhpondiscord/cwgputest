Dawn / WebGPU: bounded regression probes

Runs normal, deliberately invalid, and lifecycle WebGPU API calls against the browser implementation. All tests run locally, use tiny buffers and no intentional GPU hangs or memory exhaustion. Tests check whether invalid operations are rejected safely; they do not verify C++ memory safety or confirm a Dawn vulnerability.

Run validation and lifecycle probes

Includes buffer-copy bounds, mapAsync ranges and alignment, competing mappings, destroy while mapping, staging-buffer reuse, and batched vs. sequential small readbacks. Exportable records include errors, expected behavior, timing, and environment.

No network requests. The original suite is limited to 16 KiB buffers and 12 readbacks; the follow-up suite uses at most 32 4-KiB staging buffers, and short bounded waits. Errors are classified as expected rejection / unexpected acceptance / inconclusive.

Follow-up: repeated performance + mapping lifecycle

New tests compare 1, 4, 12, and 32 staging buffers (4 KiB each), in sequential and batched modes. The test alternates case order across rounds, verifies every buffer, and reports median, mean, minimum, maximum, p95, and median speedup. Five additional mapping lifecycle checks exercise cancellation, duplicate pending maps, legal remapping, and destruction.

Bounded local tests; no native D3D12 fault injection, oversized allocations, or network access. All 4-KiB copies are data-validated. Treat unexpected behavior as a lead for investigation, not proof of a native vulnerability.

Checkpoint overlap / bounded staging pool

Compare blocking checkpoint capture against asynchronous staging-buffer maps while subsequent GPU dispatches are submitted. Both modes create the same number of intermediate snapshots, validate every byte of GPU state, and use a fixed 1–4 staging-buffer pool. The overlapped mode waits for the oldest pending map only when the pool is full; work is still ordered on the same GPU queue.

The test measures application-level pipeline scheduling; it cannot prove native GPU copy/compute concurrency. Both approaches use one compute submission per dispatch, keeping submission-count comparisons consistent.

Native D3D12 fault-model harness

A standalone C++ test harness for the residency-lock error-unwind and fence-registration error-reporting paths is provided in native-dawn-tests. This exercises modeled control flow, not the actual Chromium/Dawn D3D12 implementation. True fault injection must be integrated into a local Windows Dawn build; the Space cannot execute native D3D12 tests.

Scope and limitations

The suspected D3D12 native mapping-error residency lock issue requires injected ID3D12Resource::Map failure and residency-lock inspection in a local Dawn build; browser JavaScript cannot test that invariant directly. D3D12 SetEventOnCompletion HRESULT handling likewise needs a native failure-injection test. Arithmetic in DynamicUploader::Reserve and CopyTextureData requires native boundary/validation tests; this page deliberately does not attempt huge sizes or malformed wire messages.
